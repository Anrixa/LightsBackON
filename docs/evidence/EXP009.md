# EXP009 — Dynamic Mission Consequences and Fault Propagation

**Engineering branch:** `task/EXP009-mission-consequences`. Source baseline: EXP008 commit `6d9d1d0f373a700e4f193609db2b02e854708589`, draft PR #193. EXP009 is a stacked, opt-in experimental source phase, **not merged to main** and **not gameplay/release certified**.

## Implementation

- `scenes/expeditions/consequence_chains.json` defines **200 explicit source-bound cascade profiles, 600 linked service nodes, 200 certification consoles and 800 interactable IDs**. Profiles pin the EXP01 level/location/puzzle identity and EXP08 scenario/graph/fault identity.
- Eight real service domains are represented: distribution, transport, health, commerce, waterworks, communications, education and shelter. Each node names a specific local service and a consequence of failure, rather than renaming a generic timer.
- Both **forking (67)** and **serial (133)** failure dependencies are implemented. Every node has its own bounded source-authored exposure threshold. A failed upstream node activates dependent service nodes; earlier mitigation activates downstream inspection while averting an upstream failure. Faulted EXP08 state and unsafe host electrical/hazard readings accelerate propagation.
- Each service supports a meaningful process: **survey → isolate (actual SPUR OFF)**, **survey → divert (actual SPUR ON, finite one-use reserve)**, or **survey → repair after failure (SPUR OFF, safe hazard state, parent restored/contained)**. Repairs are ordered by dependency; neither response falsely claims the electrical grid has physically repaired itself.
- Even after EXP08 certification, unresolved consequences block extraction. A completed consequence certification is **reopened if real host supply, safety or EXP08 status drops**. Incident counts, recovery counts, diversions, reopening counts and a bounded event log remain in the session's canonical authoritative state. No new credits, field points, saves or production contract result types were invented.
- `SessionHost` accepts only the `operate_consequence` intent with a single string action; the existing peer-admission, sequence-dedupe, rate, range and optional physics-LoS gates remain mandatory. Source-defined targets are never accepted from the network. The new state and host tick are covered by the existing authoritative revision/hash/delta pipeline.
- First-person experimental graybox presentation gets service terminals, a certification console, live multi-service consequence statuses and a response-choice key (`T`). Legacy C01–C12 and opt-out EXP03–EXP08 sessions preserve their previous start signatures, authority scopes, saves and results.

## Qualification and execution gates

1. Independent Python source verifier and mutation tests: all 200 source-key pins, identity checks, 800 unique targets, DAG integrity, threshold bounds, two topologies, eight domains, branch/failure/recovery reference traces and both Windows export preset memberships.
2. Godot headless integration: all 200 isolation replays; serial/fork propagation to three failures and ordered recovery; spare depletion; denied early commands; certification reopening on real supply loss; legacy opt-out; unknown peer, forged payload, replay and remote target handling.
3. Full inherited Linux and Windows `tools/run_tests.sh` suite, C01–C12 solution traces, cross-reference parity, QA57 Windows export/smoke; exact final head evidence.
4. PR review and sequential merge prerequisites: **EXP06 #191 → EXP07 #192 → EXP008 #193 → EXP009**, then merged-main CI. No auto-merge while upstream PRs remain drafts.

**Explicit HOLD:** Human/controller route and physical playability testing, collision/ladder qualification, hardware/GPU or Steam/network release tests, approved final art, production saves/migrations, live economy/credits promotion and release certification.

**Evidence boundary:** A passing source/headless engine demonstrates the new authority and simulation behavior, not 200 independently hand-tested physical levels or a certified service network. Every source-based failure is a game system state and mission consequence, not an assertion of simulated hardware realism.
