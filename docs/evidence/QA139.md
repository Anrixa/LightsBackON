# QA139: Lower-tier GPU probes (Intel UHD iGPU, Adreno 640) on the owner's hardware

- **Status:** exploratory measurements, 8 Nov 2026. **No gate is satisfied**: the scene is the graybox, the Intel runs use renderers that
  are not the locked baseline, and Android is outside v1.0 (Windows x64 is a locked decision). No backlog status changes.
- **Baseline:** `main` 333579b (ADR-016 merged). Godot 4.7.2.stable.official.ed1daf0bf.
- **Why:** owner asked whether a lower-class GPU can be emulated on this PC, whether Intel UHD can be tested, and whether the
  Adreno 640 phone can run the game. Feeds ADR-016 section 4.2 (renderer decision by measurement).

## 1. Can a GTX 1650 be emulated on the RTX 5090? No.

No tool reproduces another GPU's memory size, bandwidth or driver behaviour. Frame caps, raised resolution or `nvidia-smi` clock locks
(admin, a system setting, often refused on laptop GPUs) change numbers that still do not predict a GTX 1650. Emulated results never satisfy
the GTX 1650-class P95 requirement (CLAUDE.md section 8). Not attempted.

## 2. Intel UHD iGPU (i9-14900HX, "RaptorLake-S Mobile Graphics Controller")

Godot lists it as Vulkan device #1 (`--verbose`). The locked Compatibility renderer (OpenGL, and ANGLE/D3D11) selected the RTX 5090 on this
hybrid laptop. Running Compatibility on the iGPU would need the Windows per-app graphics preference "Power saving", a PC setting that was
not changed.

`Godot --path . --rendering-method <m> --rendering-driver vulkan --gpu-index 1 --print-fps --disable-vsync --resolution 1920x1080 res://scenes/mission/mission_root.tscn` (30 s, idle at spawn, first 3 samples dropped):

| Renderer on Intel iGPU | FPS samples | min | median | max |
|---|---|---|---|---|
| Mobile (Vulkan 1.4.323) | 23 | 137 | 143 | 146 |
| Forward+ (Vulkan 1.4.323) | 22 | 96 | 105 | 111 |

One-second averages, not P95. The exit-time "Unreferenced static string" lines come from `timeout` killing the process.

## 3. Android: Samsung Galaxy Note10 (SM-N970U1), Snapdragon 855, Adreno 640, Android 12

Done outside the repo, in a scratch copy: the copy got an "Android Spike" export preset (arm64, `org.lightsbackon.spike`, release template signed with
the standard Android debug key) plus `textures/vram_compression/import_etc2_astc=true`. Android templates were extracted from the official
`Godot_v4.7.2-stable_export_templates.tpz` (SHA512 OK) into `%APPDATA%\Godot\export_templates\4.7.2.stable`. APK 28.4 MB. Installed over USB with
`adb`, driven with `adb shell input keyevent`, measured, then **uninstalled**.

| Check | Method | Result |
|---|---|---|
| Boot | logcat `godot` tag | OpenGL ES 3.2 V@0502.0, Compatibility, Adreno 640; `am start -W` TotalTime 808 ms |
| Rendering | `adb exec-out screencap` at 2280x1080 | HUD, objectives, tool bar, graybox street, tablet map and evidence panel correct |
| Mission idle at spawn | `dumpsys SurfaceFlinger --latency` on the SurfaceView (BLAST) layer, 4 windows | 502 frames: median 16.69 ms, **P95 16.76 ms**, P99 16.85 ms, max 17.15 ms, 0 frames over 20 ms |
| Network tablet open (Tab key event) | same, 3 windows | 375 frames: median 16.69 ms, P95 16.76 ms, max 33.38 ms (1 frame over 20 ms, likely the tablet build) |
| Memory | `dumpsys meminfo` | TOTAL PSS 242,897 KB; Graphics 71,356 KB; Native Heap 98,408 KB |

The panel runs at 60 Hz with vsync, so these results show stable 60 FPS but not the remaining headroom.

### Findings

1. **Menu "skipped" to the mission: not a defect.** A scratch-only `_input` logger in `main_menu.gd` showed a real `InputEventScreenTouch`
   at (1055, 923), emulated as a left click, about 2.3 s after boot, which pressed the focused Start/Continue button. A matching left click was
   seen on Windows. No auto-start path exists in `boot.gd` or `main_menu.gd`.
2. **`DisplayServer.keyboard_get_label_from_physical` is unsupported on Android** (`scripts/ui/ui_text.gd:111`): about 8 engine errors while the HUD
   builds its key labels, then none. Harmless on Windows; a mobile port would need a guard and touch glyphs.
3. **No project icon is set** (`application/config/icon`): the Android export reports it as an error. The Windows export reported no error.
   Belongs to branding/release work.
4. **The game is not playable by touch.** The phone run worked only through emulated key events. A port would need touch controls, a product
   decision outside v1.0.

## 4. Exported Windows menu spread (QA138 follow-up)

QA138 recorded the exported Windows menu at 540-2585 FPS. In order, the samples drop to mission level (about 550) after second 15. This is
consistent with the same kind of click starting the shift during the run, not with a rendering problem. Not re-measured.

## Not verified

phone, controller, and anything network-related.
