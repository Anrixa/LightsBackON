## Method

1. **New internal-only scenario driver** `scripts/diagnostics/qa140_scenario_driver.gd`, started by `boot.gd` only with
   `-- --qa56-capture --qa56-id=<hex> --qa140-scenario` on an internal or editor build (release exports print
   "QA140 scenario is not available in this build"; verified on the exported release build, run `release_gate`). It plays the QA56 route
   unattended through the normal input path (`InputEventAction` / `Input.action_press`): menu idle 20 s, the menu's own Start button, mission
   idle 30 s, walk + pad-look 40 s, 20 tablet open/close cycles, 10 pause open/close cycles, final idle 20 s, normal quit. It marks one QA56
   segment per step, verifies each tablet/pause toggle actually changed the panel, records engine render monitors per segment, and logs every
   real (non-driver) key/mouse/touch/joypad event.
2. **QA56 frame probe** (`scripts/diagnostics/qa56_frame_probe.gd`) writes the per-frame main-loop interval CSV.
3. **Target runner** (session scratch, not in the repo): starts the exported exe with `APPDATA` redirected into the test folder (no user
   profile touched), samples Windows working set, private bytes and per-process `GPU Process Memory` dedicated/shared counters every 2 s,
   and copies the outputs back.
4. **GPU selection.** Compatibility (OpenGL): the per-app Windows graphics preference for the test exe only
   (`HKCU\Software\Microsoft\DirectX\UserGpuPreferences`, 2 = GTX 1650, 1 = Vega/Intel), removed afterwards. Vulkan (Mobile, Forward+):
   `--gpu-index`. **Finding:** on the Ryzen laptop the Windows preference re-orders Vulkan devices (with preference 1 the Vega becomes
   device #0); on the owner's PC it does not (Intel stays #1). Always read the adapter from the boot line; `frames_qa140.json` records it.
5. `python tools/qa140_summarize.py <results>` computes nearest-rank P50/P95/P99/max per run and per segment, first 5 s excluded.

Commands per run (target): `LightsBackOn.exe --log-file <run>\godot.log <renderer args> -- --qa56-capture --qa56-id=<id> --qa140-scenario`,
renderer args one of `--fullscreen --disable-vsync` | `--resolution 1280x720 --disable-vsync` | `--fullscreen` (vsync on) |
`--fullscreen --disable-vsync --rendering-method mobile|forward_plus --rendering-driver vulkan --gpu-index N`.

### What this shows

1. **The graybox is far inside budget on all three GPUs under the locked Compatibility renderer.** P95 is 3.2-4.0 ms at 1080p on the
   GTX 1650 and Vega 10 (about 4x headroom against 16.7 ms) and 7.8 ms on Intel UHD at 2560x1600. The GPU is not today's constraint; the
   frame budget is available for art. This says nothing about the cost of a lit, textured scene.
2. **Forward+ is the expensive option on integrated GPUs**: about 2.2x Compatibility on the Vega (mission P95 10.1 ms) and 1.7x on Intel,
   with multi-second first-load stalls (2.2 s Vega, 4.5 s GTX 1650) from pipeline compilation, and 2-3x the working set. Mobile sits near
   Compatibility on frame time but uses about 2x the working set and 3-5x the engine video memory. Keep Compatibility as the baseline until the
   ADR-016 lookdev scene is measured the same way.
3. **Vsync on at 120 Hz**: median 8.3 ms as expected; P95 11-12 ms means occasional missed vblanks on both hybrid paths, and 12-13 frames
   over 33 ms per run, mostly at mission load. Not investigated further on a graybox.
4. **Load stalls**: the worst frame of every run is the menu-to-mission transition (220-710 ms Compatibility). A loading screen or shader
   warm-up belongs on the design list, not the performance-defect list.
5. **No rising memory** across the 3-minute route: the working set over the last 20 s minus that at one third of the run ranges from
   -135 to +15 MiB across all runs (`working_set_late_minus_mid_mib` in `summary.json`), so tablet/pause cycling does not accumulate. A
   3-minute run cannot prove the absence of a slow leak.

## Defects found and fixed in this branch

1. **QA56 frame probe recorded no frames (tooling, would have voided the physical QA56 run).** `boot.gd` added the probe with
   `get_tree().root.add_child()` during boot `_ready()`, which Godot refuses ("Parent node is busy setting up children"), so the probe never
   entered the tree and every CSV was header-only. Now `add_child.call_deferred(probe)`; regression test
   `test_QA140_boot_adds_diagnostics_nodes_deferred`.
2. `Performance.MEMORY_STATIC` is always 0 in release templates; the driver no longer reports it (Windows counters are the memory source).

## Other findings

- **Unexpected Start presses were real input.** Four of the first remote runs and two local runs entered the mission before the driver pressed
  Start. The driver's input log shows real left clicks on the menu (`nv_gl_1080_r2`: click at (1009, 841) at 8.7 s, then another in the
  mission; `intel_gl_1080`: a click at 2.4 s plus W/Up keys and Escape while the owner's PC was in use). This matches QA139's "menu skipped"
  observation and is not a code path. The driver now records such runs instead of aborting; `intel_gl_1080` frame data was taken with a person
  using the PC (one pause cycle disturbed) and `nv_gl_1080_r2` is flagged `shift_started_before_driver`.
- **SSH outage mid-session (not caused by the game).** At 02:20:44 another Claude session's cleanup task (`NH_Cleanup_SSH`, from a different
  project) removed the OpenSSH Server capability and its firewall rules on the shared test laptop. Target logs showed no freeze and no reboot.
  Two concurrent sessions must not share one test device without coordination.
