## Root cause

The shipping `scripts/ui/main_menu.gd::_ready()` allocated an unparented `Button.new()` into the `start_button` field **before** reading offline checkpoint status. Later in the same method, it created another `Button.new()` into the same field, overwriting the first Node reference without ever adding the first Button to the scene tree or calling `free()`. Unlike `RefCounted`, an unparented `Node` is not automatically reclaimed when its GDScript reference is overwritten.

The previous QA53/QA54 investigations isolated leftover TextServer FontRID/ShapedText and CanvasItem exit warnings to the actual `MainMenu._ready()` path; synthetic controls, themed Labels, and dialogs on their own had zero warnings.

- `test_QA55_start_button_created_once` rejects duplicate `Button.new()` assignments.
- `test_QA55_start_button_owned_by_menu` confirms the user-visible start action is parented in the live scene.

The red Linux CI job in [run #41973654224](https://github.com/Anrixa/LightsBackON/actions/runs/41973654224) logged: **265 passed / 1 failed / 8,251 assertions**, with `test_QA55_start_button_created_once` FAIL and live ownership PASS. The workflow was later cancelled by a new commit; the red assertion result was observed in its preserved Linux job log and is **not** represented as a completed overall run.

### Minimal correction

Removed exactly the **first**, unparented `start_button = Button.new()`. The existing later allocation, `pressed` signal connection, correct menu parent and keyboard/controller focus remain unchanged. The existing save-status logic still runs before the visible button is constructed; no launch, continue, saved progress or UI behavior is modified.
