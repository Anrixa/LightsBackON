## What is implemented

1. `scripts/diagnostics/qa56_frame_probe.gd` is inactive by default. Only a **windowed Windows session** with `--qa56-capture --qa56-id=<32 hex>` after the exported program's `--` option activates it through `scenes/boot/boot.gd`. It persists as a SceneTree root child through MainMenu/MissionRoot changes. It records monotonic engine main-loop frame intervals, scene category and F9-marked scenario number to a local `user://qa56/<session>.csv` file. It flushes at bounded 240-frame intervals, and on shutdown. No network, user ID, or diagnostic upload.
2. `tools/Start-QA56-WindowsCapture.ps1` launches the **actual Windows export**, hashes it, samples process working-set/private bytes every two seconds, attempts Windows per-process GPU dedicated memory counters, copies the engine's frame CSV and writes metadata. Missing Windows GPU counters remain **unknown**, never zero. It neither silently terminates gameplay nor edits existing profiles.
3. `tools/qa56_analyze.py` validates strictly increasing time samples and finite positive frame data, excludes the initial five-second warm-up, calculates nearest-rank P95/P99 and maximum frame interval overall and by scene, counts slow frames (>33.3ms), reports RAM/private/GPU range and first-to-last deltas, and refuses a complete-capture label without enough samples, both scenes and observed GPU data. Its output ALWAYS states `PENDING_PHYSICAL_REVIEW`; numbers alone do not prove UX, stable memory, or release approval.
4. `tests/python/test_qa56_analyze.py` covers missing data, P95 rank, warm-up, invalid samples, completeness and explicit non-approval. `tests/integration/test_QA56_capture_gate.gd` tests opt-in and 32-character hex session validation in the pinned Godot test suite.

**Metric interpretation:** The frame P95 is a Godot process main-loop interval, not compositor present-to-present latency, end-to-end input latency, or GPU execution time. Windows GPU Process Memory dedicated usage counters may be absent, driver-dependent, or include more than one adapter. First-to-last memory change is not sufficient to establish a leak; repeat equal-duration workloads and inspect plateau and screenshot evidence.

## Exact physical test (Windows GTX1650-class)

Obtain the final, matching **Windows release export** from the source revision being assessed, with `LightsBackOn.exe` and its `.pck` alongside it. Use the repo's normal Windows Desktop export preset; never use a headless CI launch as substitute for these observations.

In Windows PowerShell from a clean checkout of that exact source commit:

```powershell
$ErrorActionPreference = "Stop"
Set-Location C:\LightsBackOn
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Start-QA56-WindowsCapture.ps1 `
  -Executable .\build\windows\LightsBackOn.exe `
  -OutputDirectory .\build\qa56 `
  -MaxSeconds 900 -SampleSeconds 2
```

The script prints a random session ID. In the actual windowed exported build, do the following **in one continuous capture**, using F9 to increment the scenario marker on each change:

1. Idle main menu 60 seconds, resize to 720p and 1080p and inspect clear title/focus.
2. Start a new offline shift; walk the first repair path for at least 90 seconds, inspect the HUD and visual restoration.
3. Repeatedly open/close the tablet and switch Network/Objectives (at least 20 times); vary UI scale between 80% and 150%.
4. Repeatedly open/close accessibility and pause overlays (at least 20 times); verify Reduce Flashes/Motion applies immediately and after exiting/reopening.
5. Return to the menu, inspect Continue/New Shift confirmation and focus, then use the application's **Quit** action. Do not force-kill; exiting normally flushes the final frame batch. The script leaves the game running if its timeout is reached.

The script saves `metadata.json`, `frames.csv`, `resources.csv` and `report.json` under `build/qa56/<session>/` (local, not tracked). It prints `QA56_CAPTURE_COMPLETE_FOR_REVIEW` only when dataset completeness gates pass. For absent GPU counters or incomplete scene coverage it exits nonzero and names the missing evidence. Preserve screenshots/video separately; don't upload private profile paths, account IDs or hardware serial numbers.

For repeated plateau analysis, run two comparable captures, keep Windows power mode/resolution constant, and compare report ranges and memory graphs. Record exact Windows build and driver, target GPU and resolution, P95 intervals for both scenes, max stalls, peak working set/private and available dedicated GPU memory, checkpoint/quit correctness, and any controller-only issue. If memory shows unbounded growth, frame pacing worsens, or a P0/P1 interaction defect appears, keep #51 open and fix before release.
