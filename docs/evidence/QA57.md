## Why this is a separate follow-up

QA56 introduced opt-in `user://qa56` performance capture, with P95 frame-loop intervals and process RAM/dedicated GPU counter samples. Its initial automatic completeness gate accepted both scene labels and any two F9 markers. That is not enough to establish that a **single matching exported build** actually ran the five prescribed scenarios: stale EXE/PCK/manifest combinations or a CSV pair from unrelated runs could be called complete for review without deterministic consistency checks.

This phase does **not** introduce new telemetry; it hardens the existing local-only evidence collector.

## Implemented

### 1. Build pin before launching

`tools/Start-QA56-WindowsCapture.ps1` now refuses to launch if the Windows export EXE, same-name sidecar `.pck`, or same-directory `build_manifest.json` is missing. Its manifest must declare Godot `4.7.2`, a clean, 40-hex Git commit, and the same source HEAD as the local checkout. The exact EXE, PCK, and manifest SHA256 hashes plus source commit and build ID are recorded in local capture `metadata.json`. During the real windowed run, the wrapper also passes Godot's `--log-file` and verifies the **actual running PCK boot line** against the manifest build ID and pinned 4.7.2 engine; `godot.log` and its SHA256 digest become part of the same integrity evidence. Merely placing an unrelated sidecar manifest beside an old PCK is insufficient.

`-PreflightOnly` checks those constraints **without launching any game or collecting GPU data**; the Windows CI workflow calls it after Windows release export, PCK creation and manifest copy. A green CI preflight does not qualify real Windows rendering.

### 2. Capture integrity receipt and scenario review

On normal exit, the PowerShell wrapper hashes `frames.csv` and `resources.csv` and binds those digests, process exit state, output manifest and hardware-reported driver version to the local metadata. The existing QA56 statistics report continues to calculate frame P95/P99, memory and missing-GPU conditions.

The new `tools/qa57_integrity.py` separately rejects:
- missing/malformed source/build/EXE/PCK/manifest provenance, changed CSV checksums, missing/modified engine boot log or a runtime build ID mismatch;
- an abnormal or nonzero game exit, timeout, insufficient QA56 base completeness, or any claim of release approval;
- insufficient raw samples (<1,000 frames or <30 process samples), <20 dedicated GPU samples, invalid sample periods outside 1..10 seconds, mismatched sample counts or a material frame/process timeline mismatch;
- nonmonotonic, nonfinite or discontinuous engine frame intervals (the recorded `frame_ms` must agree with adjacent elapsed timestamps to 0.015 ms);
- missing, out-of-order, too-short or wrong-scene F9 stages.

Required **post-warmup observed duration** for F9 segments:

| Segment | Expected scene | Minimum duration | Intended runbook operation |
| --- | --- | --- | --- |
| 0 | MainMenu | 30 s | Inspect menu and initial focus |
| 1 | MissionRoot | 60 s | First repair path |
| 2 | MissionRoot | 30 s | Tablet and network/objectives reflows |
| 3 | MissionRoot | 30 s | Pause/accessibility overlays |
| 4 | MainMenu | 20 s | Return menu, then quit normally |

Each stage must contain >=60 recorded frames and >=75% frames with its expected scene label. These are deliberately **minimal completeness thresholds**. The tool cannot determine whether 20 tablet reflows, physical controller interactions, rendered contrast or actual restoration were observed; those remain human/hardware evidence, not inferred from synthetic F9 markers.

A complete self-consistent session writes `integrity.json` with `COMPLETE_FOR_PHYSICAL_REVIEW` and an explicit `PENDING_PHYSICAL_REVIEW` release gate. Failed checks write `INCOMPLETE` with exact reasons; the wrapper exits nonzero. No upload or user/account identifiers are collected.

### 3. Reproducible source UIDs (an actual CI blocker)

The first Windows packaging validation correctly **refused** `QA57_DIRTY_BUILD_REJECTED`: generated `*.gd.uid` sidecars were untracked after headless Godot import. [Windows CI run #41996105439](https://github.com/Anrixa/LightsBackON/actions/runs/41996105439) showed exactly 29 affected paths, including production gameplay scripts and diagnostic/integration tests. Such UIDs are resource identities, not disposable compilation caches: Godot's [official UID guidance](https://godotengine.org/article/uid-changes-coming-to-godot-4-4/) says to **commit** them and not ignore `*.uid`.

Committed all 29 **actual engine-generated Windows UID values** in one atomic Git tree commit, preserving stable references across future Windows and Linux checkouts. Windows CI now fails explicitly if another Godot import creates untracked script UID sidecars, instead of publishing a mysteriously dirty manifest or silently bypassing that requirement.

This was a real source/export reproducibility defect identified by QA57, not a changed gameplay feature.

### 4. Regression protection

`tests/python/test_qa57_integrity.py` checks one complete **synthetic** sequence and sixteen negative/malformed scenarios: altered frame checksum, unpinned build, abnormal exit, missing tablet stage, wrong-scene pause stage, out-of-order marker, short final menu, stale resource CSV, unavailable GPU values, false release claim and sample mismatch/nonfinite timeline. These are **offline parser tests**, never physical GPU measurements.

`bash tools/run_tests.sh` runs all Python tests and the existing Godot source tests. Windows CI also parses and preflights the PowerShell script, then exports/smoke-tests the release binary.

## Exact command for physical capture

From a **clean checkout matching the exported package's** `build_manifest.json.git_commit`, with `build/windows/LightsBackOn.exe`, `LightsBackOn.pck` and `build_manifest.json` all in the same directory:

```powershell
Set-Location C:\LightsBackOn
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Start-QA56-WindowsCapture.ps1 `
  -Executable .\build\windows\LightsBackOn.exe `
  -OutputDirectory .\build\qa56 `
  -MaxSeconds 900 -SampleSeconds 2
```

Record F9 segment transitions **only** when moving to the next scenario. Start on menu in segment 0; press F9 once after entering the mission (segment 1), once at the tablet stage (2), once for overlays (3), once after returning to the main menu (4); leave each stage running at least its minimum duration and quit normally through the game. The script collects `metadata.json`, `frames.csv`, `resources.csv`, `godot.log`, `report.json`, `integrity.json` in `build/qa56/<random-session-id>/`.

A human must still inspect UX and hardware evidence. Neither a complete integrity report nor GitHub CI implies target GPU, Steam or launch qualification.
