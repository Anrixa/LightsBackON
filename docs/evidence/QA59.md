## Observed gap and change

QA58 compares complete 720p and 1080p runs, but a whole-run P95 can mask a poor first repair, repeated tablet reflow, or accessibility overlay interaction. Its 95% dominant-viewport tolerance also does not enforce the manual runbook's instruction to keep the viewport fixed through an entire post-warmup session.

QA59 adds tools/qa59_scenario_review.py:

1. Load each of the **four complete capture directories** through the unchanged QA58 validator, repeating QA56 raw-data statistics and QA57 hashes/engine identity, process chronology and F9 duration checks. Detect changes to the frame CSV between validation and analysis.
2. Require **every post-warmup viewport measurement** to match exactly 1280×720 or 1920×1080 for the chosen run. A single resizing event now prevents QA59 scenario qualification, even if QA58's dominant viewport was 95% or more.
3. Recalculate Godot main-loop frame **P95, P99 and max** for each of the five named F9 scenarios and for each observed scene within the scenario. Include sample counts, duration, expected-scene coverage and share of intervals over 33.3 ms.
4. Compare scenario-specific P95 across the two independent captures at each resolution. P95 over 33.3 ms raises a **triage trigger**, not a release failure/success or a rendering-performance claim. Preserve all original QA58 cross-run memory/GPU and package-identity gates.
5. Write only local JSON. Do not infer that F9 markers demonstrate actual repairs, tablet actions, a physical GPU, monitor presentation timing or controller navigation.

**Deliberate limitation:** the Windows process counter clock begins before the Godot probe's elapsed-time clock. Assigning RAM/VRAM counters to an exact F9 scenario would be potentially misleading without explicit clock synchronization. QA59 therefore retains whole-run memory comparison via QA58 and limits per-scenario measurements to the trustworthy Godot frame stream.

## Physical Windows command — only after actual QA58 captures exist

Use the four real build/qa56/<random-session-id> directories created by the [QA58 runbook](QA58.md). Keep source checkout, exported EXE/PCK/manifest and operating conditions fixed. After validating each session with QA57 and the four-session QA58 comparison, run:

~~~powershell
Set-Location C:\LightsBackOn
py -3 -m tools.qa59_scenario_review `
  --capture .\build\qa56\CAPTURE1 `
  --capture .\build\qa56\CAPTURE2 `
  --capture .\build\qa56\CAPTURE3 `
  --capture .\build\qa56\CAPTURE4 `
  --output .\build\qa59-scenario-review.json
~~~

A technically consistent report returns QA59_SCENARIO_REVIEW=COMPLETE_FOR_MANUAL_REVIEW. Rejected inputs return INCOMPLETE with exit code 2. Neither state automatically approves release.

A human must cross-reference stage time ranges to redacted **real** screen/video captures, verify 20+ actual tablet changes and pause/accessibility transitions, play the first repair with a physical controller and record 80–150% text legibility, window/lighting restoration, GPU/driver and measured RAM/VRAM. Do not close #51 or mark UX01/V09 DONE without those observations.
