- **Scope:** Offline C01 recovery checkpoint ordering and live-scene regressions; no save schema, content revision, authoritative recovery protocol, third-party assets, gameplay balance, Steam or engine updates.
- **Evidence status:** Implementation committed; GitHub CI verification required before merging. Do not claim a pass from unrun tests.

## Source-level defect and risk

`MissionRoot._recover_player()` dispatches the authoritative `recover_self` command synchronously, **before** teleporting the local CharacterBody3D to the van. The accepted `action_replied` signal invokes `MissionRoot._on_action_replied()`, whose generic durable-action handler previously called `_save_checkpoint()` for `recover_self`.

This saves the **old** player transform. A player who fell outside the checkpoint's legal `position_cm` bounds causes `OfflinePersistence.write_checkpoint()` to refuse `BAD_VIEW`; `MissionRoot._save_checkpoint()` then sets `_save_enabled = false`, disabling later saves even though recovery succeeds. An in-bounds pause-menu recovery similarly persists the old position rather than the van location. A subsequent Continue Shift can resume at the wrong location.

## Correction

1. Keep `recover_self` in the authoritative host command path, but exclude its reply from the generic pre-relocation autosave list.
2. After the accepted recovery, reset local position and velocity, refresh authoritative van-zone presence and **then** write the checkpoint once.
3. Preserve existing save-failure fail-closed behavior if the corrected post-teleport write encounters a genuine persistence problem. Never rewrite or migrate invalid or future-schema saves.

## Regression coverage

- `test_QA63_pause_recover_replaces_old_position_before_resume`: pause at a valid non-van location, recover, verify the checkpoint changes to the van position and gameplay resumes.
